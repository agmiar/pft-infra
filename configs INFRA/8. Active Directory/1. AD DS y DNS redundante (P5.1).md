# 1. AD DS y DNS redundante — P5.1

**Alcance:** crear el bosque pft.test en DC1, promover DC2 como controlador adicional/DNS en el otro PVE, verificar replicación inicial y configurar el DNS mínimo requerido por el frontend para resolver web.pft.test. Esta guía termina antes de P5.2 (zonas adicionales, OUs, grupos y GPO) y P5.3 (NTP).

**Estado histórico:** P5.1 está Aprobado según el cierre mínimo del Plan Unificado. Esta guía es para repetir el procedimiento; no convierte los comandos sugeridos en una transcripción del trabajo original.

## 2. Precondiciones

1. Seguir el orden acordado: P4.4 aprobado, luego P4.5 aprobado y sólo entonces P5.1. La cronología histórica no siguió estrictamente este orden: P5.1 se cerró antes de la prueba P4.5; después P4.5 se revalidaron quorum, estado de ambos DC y consultas SRV. No se repitieron dcdiag ni repadmin durante esa revalidación posterior: sus aprobaciones corresponden a las lecturas originales de P5.1. Para una defensa explicar la desviación, no ocultarla.
2. Ambos PVE deben estar en PFT-CLUSTER, con QDevice y quorum 3/3. Revisar que pvesr no tenga tareas y que ha-manager no tenga recursos de VM.
3. Capturar preestado del clúster, VMs, almacenamiento, capacidad del anfitrión, red/DNS de cada invitado y estado GNS3. La exención histórica del umbral de espacio fue puntual y no equivale a una medición de capacidad; medir los recursos disponibles antes de instalar.
4. Confirmar PVE-1 y PVE-2 como hosts separados para DC1 y DC2, segmento VLAN 50, gateway y medios locales disponibles. Si hay discrepancias de IP/MAC o capacidad, detenerse.
5. No guardar contraseñas de Administrator ni DSRM en comandos, capturas, guías ni evidencia. Introducirlas sólo en los prompts interactivos autorizados. No registrar los valores.

## 3. Crear las VMs e instalar Windows

1. En la interfaz de PVE-1, elegir Create VM y completar General (VMID 101, DC1-PFT), OS (medio Windows local), Disk (local-lvm, thin, 60 GiB), CPU (2), Memory (2048 MiB) y Network (e1000 sobre vmbr0). Adjuntar el medio de drivers aprobado si hace falta para almacenamiento/red. La evidencia también muestra QEMU Guest Agent habilitado en la configuración PVE; eso no prueba por sí solo que el agente esté instalado y activo dentro de Windows.
2. En la interfaz de PVE-2, repetir para VMID 102, nombre DC2-PFT y el mismo perfil. Confirmar antes que VMID 102 no está ocupado. El registro histórico no conserva el controlador de disco, firmware ni orden de boot; elegirlos según el medio Windows/drivers disponible y guardar el valor efectivo en la nueva evidencia. No añadir HA ni replicación.
3. Instalar Windows Server 2022 Standard Evaluation Server Core. Configurar el nombre del servidor DC1-PFT o DC2-PFT usando la consola/SConfig y reiniciar. Cambiar la contraseña inicial de Administrator durante la primera sesión mediante el prompt de Windows; no copiarla a texto plano.
4. Capturar la salida real de Get-NetAdapter y Get-NetIPAddress. Seleccionar la interfaz conectada a vmbr0 por MAC e índice observados; no asumir el número de interfaz. El registro histórico vio una NIC Intel PRO/1000 como adaptador 1 en DC1.

## 4. Fijar red y crear el primer bosque

En cada Windows Server, usar la interfaz confirmada en el paso anterior. Los comandos siguientes son una receta de repetición basada en el diseño; reemplazar el índice sólo después de verificarlo. No copiar la dirección de DC1 a DC2:

    Get-NetAdapter | Format-Table Name, InterfaceIndex, Status, MacAddress
    $IfIndex = <indice confirmado de la NIC de VLAN 50>

En DC1, usar:

    New-NetIPAddress -InterfaceIndex $IfIndex -IPAddress 192.168.50.12 -PrefixLength 27 -DefaultGateway 192.168.50.1
    Set-DnsClientServerAddress -InterfaceIndex $IfIndex -ServerAddresses @('192.168.50.12')

En DC2, antes de promoverlo, usar:

    New-NetIPAddress -InterfaceIndex $IfIndex -IPAddress 192.168.50.13 -PrefixLength 27 -DefaultGateway 192.168.50.1
    Set-DnsClientServerAddress -InterfaceIndex $IfIndex -ServerAddresses @('192.168.50.12')

Tras promover DC2 y comprobar la réplica, establecer el DNS final cruzado:

    # En DC1
    Set-DnsClientServerAddress -InterfaceIndex $IfIndex -ServerAddresses @('192.168.50.12','192.168.50.13')
    # En DC2
    Set-DnsClientServerAddress -InterfaceIndex $IfIndex -ServerAddresses @('192.168.50.13','192.168.50.12')

En cada host, verificar:

    Get-NetIPAddress -InterfaceIndex $IfIndex
    Get-DnsClientServerAddress -InterfaceIndex $IfIndex
    ping 192.168.50.1

En DC1, instalar AD DS y promover un bosque nuevo. Install-WindowsFeature AD-Domain-Services -IncludeManagementTools se registró como exitoso en la preparación histórica de DC1. El comando de promoción no quedó guardado literalmente; el ejemplo de abajo sigue la sintaxis documentada de Windows Server y pide la contraseña DSRM interactivamente:

    Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
    Install-ADDSForest -DomainName 'pft.test' -DomainNetbiosName 'PFT' -InstallDNS

Confirmar el resumen del asistente/PowerShell y dejar que complete el reinicio. Iniciar sesión como PFT\Administrator mediante el prompt de Windows. Verificar:

    Get-Service DNS,Netlogon,NTDS
    dcdiag /test:dns /v
    Resolve-DnsName _ldap._tcp.dc._msdcs.pft.test -Type SRV -Server 192.168.50.12

No avanzar a la promoción de DC2 si DC1 no responde en la red, el servicio DNS/NTDS no está activo o la prueba DNS falla.

## 5. Agregar DC2 y configurar DNS cruzado

1. En DC2 confirmar hostname DC2-PFT y configurar 192.168.50.13/27 con gateway 192.168.50.1. Antes de promover, configurar como DNS el DC1 192.168.50.12 para resolver pft.test. Esta secuencia temporal es una instrucción de repetición; la captura histórica no guardó el detalle completo de DNS previo a promover DC2.
2. Verificar resolución de dc1-pft.pft.test y conectividad con DC1. Instalar el rol y promover DC2 como DC adicional con DNS, solicitando las credenciales y DSRM en los prompts interactivos:

    Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
    Install-ADDSDomainController -DomainName 'pft.test' -InstallDns -Credential (Get-Credential 'PFT\Administrator')

3. Completar el reinicio. En DC1 dejar DNS preferido .12 y alternativo .13; en DC2 dejar DNS preferido .13 y alternativo .12. Usar Set-DnsClientServerAddress con el índice de NIC confirmado, no copiar el índice de otro invitado.
4. Esperar la convergencia. En ambos DC ejecutar:

    dcdiag /test:dns /v
    repadmin /replsummary
    Resolve-DnsName _ldap._tcp.dc._msdcs.pft.test -Type SRV -Server 192.168.50.12
    Resolve-DnsName _ldap._tcp.dc._msdcs.pft.test -Type SRV -Server 192.168.50.13

   Aceptar sólo cuando ambos DNS respondan con los registros de DC1-PFT y DC2-PFT, dcdiag termine correctamente y repadmin no informe fallos. En la ejecución histórica DC2 tuvo un primer fallo RReg transitorio durante convergencia; el reintento pasó y se conservó el evento en la evidencia.

## 6. Registro web mínimo y DNS del frontend

1. Antes de crear un registro, entrar al frontend y comprobar su IP actual con ip -br address; conservar dirección, prefijo, ruta y MAC. En P5.1 el frontend verificado fue WebUbuntuServer-1/ens3, 192.168.100.6/29, gateway 192.168.100.1. Si cambia, usar la IP real nueva.
2. En un DC crear solamente el registro A web en la zona pft.test. La ejecución histórica lo creó desde DC2, con TTL de una hora, usando la dirección real .6:

    Add-DnsServerResourceRecordA -ZoneName 'pft.test' -Name 'web' -IPv4Address '192.168.100.6' -TimeToLive 01:00:00 -ComputerName 'dc2-pft.pft.test' -PassThru

   No crear PTR ni zonas reversas en P5.1; corresponden a otra tarea. Esperar réplica y consultar el registro directamente en ambos DNS antes de cambiar el frontend. En el primer intento histórico, DC2 respondió mientras DC1 todavía devolvía NXDOMAIN; tras converger, ambos respondieron .6.
3. En el frontend capturar la configuración Netplan y una copia del archivo existente antes de editar. Mantener intactos el match/MAC, IP, prefijo y ruta actuales de ens3; añadir únicamente los nameservers bajo el bloque existente de ens3:

        nameservers:
          addresses:
            - 192.168.50.12
            - 192.168.50.13

   Aplicar el cambio desde consola o con netplan try si está disponible en esa versión, y luego comprobar:

    resolvectl status
    resolvectl query web.pft.test
    nslookup web.pft.test 192.168.50.12
    nslookup web.pft.test 192.168.50.13

   El criterio de P1.3 exige que el resolutor efectivo del frontend use ambos DNS y que web.pft.test resuelva a la IP real del frontend. P5.1 no valida HTTP/HTTPS ni un forwarder externo.

## 7. Aceptación, rollback y límites

P5.1 se cierra sólo cuando: los DC están en PVE distintos; ambos tienen AD DS/DNS y DNS cruzado; las zonas pft.test y _msdcs.pft.test están integradas con AD; dcdiag pasa, repadmin no muestra fallos y ambos DNS devuelven los registros SRV de los dos DC; el frontend consulta ambos servidores y resuelve el A web a su IP confirmada.

Si sólo falla el DNS del frontend, restaurar el archivo Netplan capturado o retirar únicamente nameservers de ens3; comprobar que IP y ruta no cambiaron. El A web se revierte por separado, sólo después de confirmar que el registro es el creado por esta tarea. No borrar la zona ni el bosque. No hay procedimiento aprobado para demover el bosque; conservar VMs y discos y detenerse si aparece un problema que requiera esa operación.

No configurar forwarder externo sin upstream comprobado. No crear zonas reversas, registros PVE/PG/VIP/Zabbix, OUs, grupos, AGDLP, GPO o NTP aquí: son P5.2/P5.3. No afirmar HTTP/HTTPS ni failover de AD/DNS.
