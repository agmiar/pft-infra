## Procedimiento aplicado: recuperación y carga inicial de GPO — 2026-09-23

### Precondición y corrección de objetos defectuosos

El inventario mostró que las cinco GPO PFT existían sólo como esqueletos: no
tenían configuración efectiva y `Set-GPRegistryValue` fallaba con
`CO_E_BAD_PATH`. Antes de corregirlas se registraron sus identificadores y
vínculos. La corrección aplicada fue limitada: se quitaron los vínculos de esos
objetos vacíos, se eliminaron sólo esas GPO defectuosas y se crearon de nuevo
con **el mismo nombre y el mismo destino**. No se modificó `Default Domain
Policy`, ni se tocaron GPO ajenas.

Ejecutar únicamente si la comprobación reproduce ese defecto; no usar este
procedimiento para reemplazar una GPO que contenga configuración válida:

```powershell
Import-Module GroupPolicy

$root = 'OU=PFT,DC=pft,DC=test'
$mgmt = 'OU=MGMT-VLAN90,OU=Zones,OU=PFT,DC=pft,DC=test'
$mapa = @{
  'PFT-Baseline-Computers' = $root
  'PFT-Baseline-Users' = $root
  'PFT-LAPS' = $root
  'PFT-Domain-Audit' = $root
  'PFT-MGMT-Workstations' = $mgmt
}

# Guardar fuera de secretos el nombre, Id y destino de cada vínculo antes de cambiar.
foreach ($nombre in $mapa.Keys) {
  Get-GPO -Name $nombre | Select-Object DisplayName,Id,CreationTime,ModificationTime
}

# Sólo después de confirmar que cada GPO está vacía e inoperable:
foreach ($nombre in $mapa.Keys) {
  Remove-GPLink -Name $nombre -Target $mapa[$nombre] -ErrorAction Stop
  Remove-GPO -Name $nombre -KeepLinks:$false -ErrorAction Stop
  New-GPO -Name $nombre | Out-Null
  New-GPLink -Name $nombre -Target $mapa[$nombre] -LinkEnabled Yes | Out-Null
}
```

### Rollback acotado

### Auditoría de controladores aplicada — 2026-09-23

El preestado de DC1 y DC2 ya tenía activos `Logon` (éxito/error),
`Credential Validation` (éxito), `Security Group Management` (éxito) y
`Audit Policy Change` (éxito). Faltaba `Directory Service Changes`. Se aplicó
en ambos DC de forma directa y verificable con `auditpol`, porque las
subcategorías de auditoría no se configuran con `Set-GPRegistryValue`:

```powershell
auditpol /set /subcategory:'Directory Service Changes' /success:enable /failure:disable
auditpol /get /subcategory:'Logon','Credential Validation','Security Group Management','Directory Service Changes','Audit Policy Change'
```

La salida posterior confirmó `Directory Service Changes: Success` en ambos.
Es una configuración local uniforme de los dos DC, no una afirmación de que la
GPO distribuya todavía sus subcategorías. Para revertir este único cambio:

```powershell
auditpol /set /subcategory:'Directory Service Changes' /success:disable /failure:disable
```

Para retirar un valor recién aplicado, usar `Remove-GPRegistryValue` sobre el
nombre, clave y valor exactos. Para deshabilitar una política sin borrar su
historial, quitar únicamente su vínculo con `Remove-GPLink`. No hay rollback
genérico que restaure los cinco objetos anteriores porque estaban defectuosos;
se conservó su preestado en la evidencia. No eliminar usuarios, OUs, zonas o
GPO válidas como parte de este rollback.

## Procedimiento manual aplicado: cuentas de laboratorio — 2026-09-23

Las identidades de demostración se crean solamente después de capturar el

usar el valor sólo en memoria.

```powershell
Import-Module ActiveDirectory

$ou = 'OU=Service-Accounts,OU=PFT,DC=pft,DC=test'
$mapa = @{
  'lab-pve-admin'    = 'GG_MGMT_PVE_ADMINS'

  'lab-db-admin'     = 'GG_DB_ADMINS'

}

foreach ($sam in $mapa.Keys) {
  if (Get-ADUser -Filter "SamAccountName -eq '$sam'" -ErrorAction SilentlyContinue) {
    throw "La cuenta ya existe: $sam"
  }
  $clave = Read-Host "Contraseña para $sam" -AsSecureString
  New-ADUser -Name $sam -SamAccountName $sam -UserPrincipalName "$sam@pft.test" `
    -Path $ou -AccountPassword $clave -Enabled $true -ChangePasswordAtLogon $false
  Add-ADGroupMember -Identity $mapa[$sam] -Members $sam
}

repadmin /syncall /AdeP
```

del GG indicado. No usar `PasswordNeverExpires` sin una decisión explícita de
diseño. Para rollback, deshabilitar primero la cuenta y removerla del GG; no
borrar objetos sin orden expresa del operador.

## Recuperación posterior al reinicio: PVE y WinRM — 2026-09-22

Esta secuencia se ejecutó para recuperar la plataforma después de reiniciar
LaptopUbuntu. Se conserva porque permite repetirla manualmente. No anotar ni
pegar contraseñas en este documento ni en las evidencias.

### 1. Recuperar el acceso temporal al laboratorio

En Ubuntu, si el puente no existe tras un reinicio:

```sh
sudo ip link add name br-pft-transfer type bridge
sudo ip addr add 172.31.255.1/24 dev br-pft-transfer
sudo ip link set br-pft-transfer up
```

Iniciar Cloud1 y verificar que el tap de GNS3 quede como esclavo del puente.
Esto no sustituye la VLAN productiva 50 ni debe modificar la ruta por defecto.

### 2. Reparar la red de gestión PVE cuando los nodos no forman quórum

Desde la consola de cada switch de acceso, leer primero:

```text
show interfaces GigabitEthernet0/3 switchport
show interfaces trunk
```

En este montaje Gi0/3 de ADvIOS-9a corresponde a PVE-1 y Gi0/3 de ADvIOS-9b
corresponde a PVE-2. Si el preestado muestra VLAN 1, aplicar en **cada**
switch:

```text
enable
configure terminal
interface GigabitEthernet0/3
switchport mode access
switchport access vlan 50
end
write memory
show interfaces GigabitEthernet0/3 switchport
```

Validar desde PVE-1 antes de encender máquinas dependientes de quórum:

```sh
ping -c 3 192.168.50.11
pvecm status
```

El resultado esperado es ping sin pérdida y `Quorate: Yes` con dos nodos más
QDevice. Rollback sólo si se decide explícitamente revertir la red: en el
puerto afectado `switchport access vlan 1`, seguido de `write memory`.

### 3. Iniciar los controladores y verificar el transporte WinRM

Cuando el clúster ya es quorate:

```sh
# En PVE-1
qm start 101
qm status 101

# En PVE-2
qm start 102
qm status 102
```

Esperar el arranque real de Windows y comprobar desde PVE-1, sin autenticar:

```sh
timeout 3 bash -c '</dev/tcp/192.168.50.12/5985' && echo DC1-WinRM-abierto
timeout 3 bash -c '</dev/tcp/192.168.50.13/5985' && echo DC2-WinRM-abierto
```

Si los puertos permanecen cerrados, abrir la consola de la VM y comprobar el
estado local, sin modificar AD todavía:

```powershell
Get-Service WinRM
Test-WSMan localhost
winrm get winrm/config/service
```

Si WinRM está detenido o no es automático, restaurarlo:

```powershell
Enable-PSRemoting -Force
Set-Service WinRM -StartupType Automatic
Restart-Service WinRM
Test-WSMan localhost
```

Antes de probar Kerberos desde PVE-1, confirmar de forma interactiva la
credencial vigente de `PFT\Administrator`. Efectuar una sola prueba `kinit
Administrator@PFT.TEST`; ante `Password incorrect`, detenerse y corregir la
credencial desde la consola del DC. No realizar variaciones ni guardar la
contraseña en comandos, scripts o evidencias.

La evidencia real de este evento está en el [incidente P4.2](../../.agents/evidencias/P4/2026-09-22_P4.2_PVE_red_incidente.md) y el [postestado P5.2](../../.agents/evidencias/P5/2026-09-22_P5.2_PVE-1_post.txt).

### 4. Autenticar WinRM por Kerberos desde PVE-1

Este es el canal administrativo que permitió retomar P5.2. En PVE-1 deben
estar instalados `krb5-user`, `python3-winrm` y
`python3-requests-kerberos`, y `/etc/krb5.conf` debe conocer el reino
`PFT.TEST`. Confirmar primero que los nombres de DC resuelven a `.12` y `.13`
y que TCP/5985 está abierto.

Solicitar la contraseña de `Administrator@PFT.TEST` de forma interactiva y
crear el ticket; la entrada no se muestra en pantalla:

```sh
kdestroy 2>/dev/null || true
kinit Administrator@PFT.TEST
klist
```

La salida esperada de `klist` incluye un TGT `krbtgt/PFT.TEST@PFT.TEST`. Para
verificar una sesión administrativa sin guardar contraseña, ejecutar:

```sh
python3 -c 'import winrm; s=winrm.Session("http://dc1-pft.pft.test:5985/wsman",auth=("", ""),transport="kerberos"); r=s.run_ps("$env:COMPUTERNAME; whoami"); print(r.status_code); print(r.std_out.decode()); print(r.std_err.decode())'

python3 -c 'import winrm; s=winrm.Session("http://dc2-pft.pft.test:5985/wsman",auth=("", ""),transport="kerberos"); r=s.run_ps("$env:COMPUTERNAME; whoami"); print(r.status_code); print(r.std_out.decode()); print(r.std_err.decode())'
```

El resultado válido es código `0`, el nombre del DC consultado e identidad
`pft\administrator`. Si devuelve otro estado, no crear ni modificar objetos
AD; capturar el error, comprobar `nltest /sc_verify:pft.test` y
`nltest /dsgetdc:pft.test /KDC` desde un DC, y reanudar sólo al recuperar el
canal. Al finalizar la sesión, retirar el ticket temporal:

```sh
kdestroy
```

La prueba del 2026-09-23 autenticó y ejecutó el chequeo en DC1 y DC2. El
método operativo es Kerberos, no Basic. El cliente `python3-winrm` instalado
en PVE-1 no puede usar cifrado de mensaje Kerberos sobre HTTP; por esa
limitación, `AllowUnencrypted` debe permanecer `true` mientras se use ese
cliente y puerto 5985. En DC1 se dejó `Basic=false`. Migrar a un listener
HTTPS/5986 con certificado válido es la mejora pendiente antes de endurecer
esa opción en ambos DC.
