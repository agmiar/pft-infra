# Control P5.2 — acceso temporal a PVE-2 desde LaptopUbuntu

- Fecha: 2026-09-17.
- Proyecto: `sprint1-preview1` (`47a3267f-9b02-4e97-a0e8-0aacb46d5ffd`).
- Estado del subobjetivo: **Aprobado** sólo para el acceso temporal a la GUI de PVE-2.
- Estado de P5.2 completo: **Bloqueado**.

## Objetivo

Dar a LaptopUbuntu acceso directo a la GUI de PVE-2 reutilizando el puente temporal, Cloud1 y la segunda NIC ya documentados, sin cambiar la red productiva ni la configuración persistente del host.

## Precondiciones

- El operador solicitó expresamente aplicar el mismo acceso temporal para PVE-2.
- El procedimiento existente reserva `172.31.255.3/24` para PVE-2 en `ens4`; no se inventó una dirección.
- La asignación sale del segmento temporal `172.31.255.0/24` del procedimiento [Pasar ISOs a Proxmox](../../configs%20INFRA/7.%20Proxmox/4.%20Pasar%20ISOs%20a%20Proxmox.txt): Ubuntu usa `.1`, PVE-1 `.2` y PVE-2 `.3`. Es direccionamiento manual del enlace de transferencia/gestión, no DHCP, VLAN 50 ni una ruta a Internet.
- La lectura previa confirmó `ens4` sin IP, el puente Ubuntu `.1/24` activo, el enlace Cloud1–switch y Gi0/2 conectado en VLAN 1.
- El puente, Cloud1, el switch y el acceso `.2` de PVE-1 ya existían al empezar esta tarea. En PVE-2 sólo se levantó `ens4` y se asignó `.3`; no se creó el enlace otra vez ni se modificó la red productiva.
- El [preestado](2026-09-17_P5.2_PVE-2_pre.txt) declara que la transcripción cruda de consola no se conservó y que una captura scratch falló; no se afirma un `pvecm status` pre-cambio de PVE-2.

## Comandos y acciones

- Consola local PVE-2: `ip link set ens4 up`; `ip addr add 172.31.255.3/24 dev ens4`.
- Verificación desde Ubuntu: ping, `nc` a TCP/22 y TCP/8006, `curl -k` a HTTPS/8006, ruta y tabla vecina.
- Verificación de capa 2: tabla MAC dinámica de VLAN 1 en el switch.
- Postestado administrativo por SSH interactivo: direcciones/rutas, servicios, `pvecm status` y `qm list`.

## Resultado y limitaciones

`https://172.31.255.3:8006` devolvió HTTP 200 desde Ubuntu; TCP/22 también aceptó conexiones. La ruta por defecto de PVE-2 quedó por `vmbr0` como antes. PVE-2 continúa sin quorum y DC2/VMID 102 está detenida; PVE-1 no se revalidó en la web después del cambio. Este puente alternativo no restaura Corosync/QDevice y no completa P5.2.

Las direcciones se añadieron con `ip addr`, sin editar `/etc/network/interfaces`; por tanto, `.3` no se conserva al reiniciar PVE-2. Cerrar el navegador no retira la IP. El puente de Ubuntu también se creó en ejecución y debe comprobarse/recrearse si se reinicia Ubuntu. Para entrar de nuevo se usa `https://172.31.255.3:8006` después de verificar que el puente y `ens4` siguen activos.

La carpeta canónica `.agents/evidencias/P5` no es escribible en esta sesión. Los artefactos suplementarios se guardaron dentro del proyecto en `outputs/P5`; no se intentó eludir ese permiso.

## Rollback

Retirar PVE-2 con `ip addr del 172.31.255.3/24 dev ens4` y `ip link set ens4 down`. Mantener el puente compartido mientras PVE-1 `.2` o PVE-2 `.3` lo necesiten. Para el rollback total, retirar ambos IP/ens4 y después eliminar el puente Ubuntu según el [procedimiento](../../configs%20INFRA/7.%20Proxmox/4.%20Pasar%20ISOs%20a%20Proxmox.txt).

## Siguiente paso

Mantener P5.2 **Bloqueado**. Si el objetivo es que PVE-1 vuelva a mostrar PVE-2 en el clúster, diagnosticar por separado la red productiva de Corosync/VLAN 50 y el acceso QDevice con preestado propio. No arrancar DC2 hasta revisar el estado/quorum y las condiciones del runbook.
