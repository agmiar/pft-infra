# S4.1 — aplicación local: control y evidencia

Fecha: 2026-09-25
Estado: Aprobado

## Objetivo

Preparar y desplegar la aplicación frontend/backend suministrada, manteniendo sin cambios la lógica del backend Spring Security + JWT.

## Precondiciones

- Fuentes locales en los dos ZIP entregados por el operador.
- WebUbuntuServer-1 en `192.168.100.6`.
- Docker y Compose disponibles en WebUbuntuServer-1.

## Acciones ejecutadas y consulta

1. Se construyó la imagen backend sin modificaciones de código; la comparación contra el ZIP original dio `backend_source_compare=0`.
2. Se ajustó sólo el frontend para aceptar un identificador LDAP en el campo existente `correo`, conservando el contrato JWT.
3. Se construyeron las imágenes y se levantó el stack Compose con PostgreSQL, API y web.
4. Se verificó `GET /login` con HTTP 200 y la etiqueta `Usuario LDAP o correo`.
5. Se verificó `/v3/api-docs` en la API, login de una cuenta de laboratorio existente y consulta autenticada `/api/v1/auth/user`, ambos con HTTP 200.
6. Consulta reproducible: `curl -I http://192.168.100.6/login`, `curl -I http://192.168.100.6:8080/v3/api-docs` y login sin guardar el JWT.

## Resultado

El stack local está levantado y la autenticación JWT existente responde. Los puertos observados son web 80 y API 8080; MinIO no se publicó por la restricción de red del laboratorio. Estado Aprobado para este alcance.

## Demostración en vivo

1. Encender WebUbuntuServer-1.
2. Ejecutar `docker compose -f /home/student/pft-s4/docker-compose.yml ps`.
3. Abrir `http://192.168.100.6/login` y mostrar `Usuario LDAP o correo`.
4. Autenticar con una cuenta de laboratorio autorizada y mostrar la pantalla protegida.
5. Consultar los logs sin mostrar tokens ni secretos.

## Rollback

Desde WebUbuntuServer-1: `docker compose down`; conservar las imágenes y la copia del ZIP modificado para restaurar el estado anterior del laboratorio.
