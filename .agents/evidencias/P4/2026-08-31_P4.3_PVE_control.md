# Control P4.3 — Compuerta de red anidada PVE

- **Fecha de inicio:** 2026-08-31
- **Tarea:** P4.3 — Validar `vmbr0` mediante una VM temporal en cada PVE.
- **Estado:** Aprobado

## Objetivo

Demostrar que `vmbr0` de PVE-1 y PVE-2 reenvía correctamente tráfico y MAC de invitados sobre VLAN 50, antes de crear el clúster PVE o cualquier VM definitiva.

## Precondiciones

- P4.1 aprobada: QDevice `192.168.90.28/27` activo en VLAN 90.
- P4.2 aprobada: PVE-1 `192.168.50.10/27` en ADvIOS-9a `Gi0/3` y PVE-2 `192.168.50.11/27` en ADvIOS-9b `Gi0/3`; ambos mediante `ens3` y `vmbr0` en VLAN 50.
- No existe aún clúster PVE, QDevice configurado como voto del clúster ni VMs definitivas.
- Antes de asignarlas, comprobar que las IP temporales propuestas `192.168.50.18/27` y `192.168.50.19/27` no responden ni tienen una MAC aprendida ajena en VLAN 50. Si hay conflicto, detener y elegir otras IP libres verificadas; no inferirlas.

## Comandos / acciones planificados

1. Capturar el estado previo de cada PVE y de las tablas MAC VLAN 50 de ADvIOS-9a/9b.
2. Crear una VM mínima temporal en cada PVE, cada una con una única NIC conectada a `vmbr0`, sin VLAN tag y sin DHCP:
   - `P4T-PVE1`: `192.168.50.18/27`, gateway `192.168.50.1`.
   - `P4T-PVE2`: `192.168.50.19/27`, gateway `192.168.50.1`.
3. Desde **cada** VM ejecutar y conservar las salidas de:

   ```bash
   ip -br address
   ip route
   ping -c 4 192.168.50.1
   ping -c 4 <IP_DE_LA_VM_TEMPORAL_REMOTA>
   ping -c 4 192.168.90.28
   ping -c 4 192.168.100.6
   ```

4. En ADvIOS-9a y ADvIOS-9b, verificar aprendizaje de las MAC de ambas VMs en VLAN 50 y que el tránsito remoto use el uplink/Port-channel esperado, mediante salidas equivalentes a:

   ```cisco
   show mac address-table dynamic vlan 50
   show interfaces trunk
   show etherchannel summary
   show spanning-tree vlan 50
   ```

5. Apagar y retirar las dos VMs temporales y confirmar que no quedan recursos temporales ni MAC activas asociadas. No crear el clúster hasta aprobar esta compuerta.

Ejecución parcial comprobada:

- 2026-08-31: P4T-PVE1 (VMID 901) arrancó correctamente desde Alpine y entregó consola serial. La VM permanece en modo live; no se ejecutó `setup-alpine`, no se instaló sistema y aún no se configuró red de invitado.
- 2026-08-31: se asignó `192.168.50.18/27` a `eth0` de P4T-PVE1 y se instaló la ruta por defecto vía `192.168.50.1`. La salida de BusyBox confirma la ruta conectada `192.168.50.0/27` con origen `.18`. Aún falta verificar respuesta del gateway y el resto de destinos.
- 2026-08-31: P4T-PVE1 confirmó `eth0` en estado `UP,LOWER_UP`, IP `192.168.50.18/27` y MAC `bc:24:11:b9:03:50`. El gateway HSRP `192.168.50.1` respondió 4/4 ICMP, sin pérdida; RTT mínimo/promedio/máximo `2.322/17.668/63.226 ms`. Falta la comprobación equivalente desde P4T-PVE2, los destinos remotos y las tablas MAC de switches.
- 2026-08-31: ICMP desde P4T-PVE1 hacia QDevice `.90.28` falló 4/4. `traceroute` recibió `!A` desde CorevIOS-1 `.50.2`, evidencia de rechazo administrativo. Se abrió `2026-08-31_P4.3_PVE_incidente.md`; queda pendiente probar el flujo funcional QNetd TCP/5403 y no se autoriza formar el clúster.
- 2026-08-31: la prueba funcional `nc -z -w 3 192.168.90.28 5403` desde P4T-PVE1 terminó con código `1`; QNetd no quedó alcanzable desde la VM anidada. Web DMZ `.100.6` respondió ICMP 4/4. P4.3 queda **Fallido**: sin flujo TCP/5403 a QDevice y sin segunda VM PVE-2, no se cumple la compuerta.
- 2026-08-31: tras autorizar la excepción temporal ICMP para P4T-PVE1, QDevice `.90.28` respondió 4/4, sin pérdida; RTT mínimo/promedio/máximo `3.295/7.291/16.988 ms`. El control se reabre como Pendiente: falta probar QNetd TCP/5403 desde PVE-1, verificar post/contadores de ambos Core, completar PVE-2, revisar MAC y retirar las excepciones temporales.
- 2026-08-31: PVE-1 comprobó QNetd TCP/5403 hacia `.90.28` con código de salida `0`. CorevIOS-1 registró `1 match` en el permiso permanente 75 y `4 matches` en el permiso ICMP temporal 77; CorevIOS-2 contiene las mismas líneas y está sin contadores por ser Standby. La conectividad PVE-1→QDevice queda corregida; continúan pendientes PVE-2, MACs, retiro de 77/78 y persistencia controlada de 75/76.

## Criterio de aceptación

Desde ambas VMs temporales deben responder, por `vmbr0`, el gateway HSRP `.1`, la VM temporal remota, QDevice `.90.28` y el frontend Web `.100.6`. Los switches deben aprender las MAC internas en VLAN 50 con un camino coherente. Finalmente, ambas VMs deben quedar retiradas.

## Decisión operativa — excepción ACL temporal

El operador autorizó el 2026-08-31 una excepción limitada para realizar las pruebas *in situ* de P4.3: además de los permisos permanentes QNetd de PVE-1 `.10` y PVE-2 `.11`, `VLAN_50_IN` permitirá temporalmente sólo ICMP `echo` desde P4T-PVE1 `.18` y P4T-PVE2 `.19` hacia QDevice `.90.28`.

Los permisos temporales se cargan con secuencias 77 y 78, únicamente en ambos Core y sin persistir. Se validan con las VMs temporales y se retiran (`no 77`, `no 78`) antes de guardar la configuración. No se incorporan a las ACL `PFT_*` de P3 ni permanecen después de retirar las VMs. Los permisos permanentes `.10/.11 -> .90.28:5403` usan secuencias 75 y 76.

## Resultado

2026-08-31: la comprobación inicial de PVE-1 no mostró VMs, y `pvesm status` confirmó los almacenamientos activos `local` y `local-lvm`. Posteriormente, el operador aportó una comprobación real de una ISO Linux mínima en PVE-1: `alpine-standard-3.24.1-x86_64.iso`, 352 MiB, SHA-256 `f4dd613206676c62949144c8ad75fc64582099f444dd1485bae104a60f51dd26`. El operador confirmó la misma disponibilidad y hash en PVE-2. Se creó P4T-PVE1 (VMID 901) únicamente para esta compuerta; no se modificaron ACL, QDevice, clúster ni VMs definitivas.

La precondición de medio de arranque está satisfecha. P4T-PVE1 alcanzó HSRP `.1`, Web `.100.6` y QDevice `.90.28` por ICMP; PVE-1 alcanzó QNetd TCP/5403 y el contador de CorevIOS-1 confirmó el permiso permanente.

## Aprobación manual del operador

El 2026-08-31, el operador —*human in the loop*— aprobó manualmente P4.3 y autorizó avanzar pese a no ejecutar P4T-PVE2, la prueba VM-a-VM y la verificación de MAC en ADvIOS-9a/9b. Esta aprobación se sustenta en los resultados reales de PVE-1/P4T-PVE1 registrados en esta evidencia.

La aprobación no afirma que las condiciones omitidas hayan sido verificadas. Deben retirarse las excepciones ICMP temporales 77/78 en ambos Core y eliminar las VMs efímeras. Los permisos 75/76 se conservan como corrección permanente de QNetd.

Las salidas aportadas se conservan en `2026-08-31_P4.3_PVE-1_pre.txt` y `2026-08-31_P4.3_PVE-1_inventario.txt`.

## Rollback

Si una prueba falla, detener. Apagar y retirar únicamente `P4T-PVE1` y `P4T-PVE2`; conservar capturas pre/post y revisar bridge, NIC, puertos VLAN 50, tablas MAC, trunk, EtherChannel y STP. No modificar clúster, QDevice, red de producción ni VMs definitivas como parte del diagnóstico.

Para la excepción ACL temporal, el rollback específico es retirar las secuencias 77 y 78 de `VLAN_50_IN` en ambos Core antes de cualquier `write memory`.

## Cierre técnico de limpieza — 2026-09-14

Antes de ejecutar P4.4 se verificó el estado real: las secuencias ACL temporales 77/78 no están en `VLAN_50_IN` de ninguno de los Core. Las reglas permanentes PVE→QDevice TCP/5403 continúan en la ACL activa (secuencias 80/90 en la configuración vigente). En PVE-1 no existe `/etc/pve/nodes/pve-1/qemu-server/901.conf` y `pvesm list local-lvm` no muestra volúmenes; el inventario de VMs de ambos PVE estaba vacío. P4T-PVE2 no fue creada.

La aprobación manual de P4.3 y sus limitaciones no cambian: P4T-PVE2, VM-a-VM y aprendizaje MAC no se ejecutaron. P4.4 quedó autorizado por el operador y se completó el 2026-09-14; ver [pre](2026-09-14_P4.4_PVE_pre.txt) y [resultado](2026-09-14_P4.4_PVE_prueba.txt).
