# Incidente P4.3 — ICMP P4T-PVE1 a QDevice denegado

- **Fecha:** 2026-08-31
- **Tarea:** P4.3
- **Estado:** Resuelto para el servicio QNetd el 2026-09-14; las pruebas P4.3 omitidas siguen como limitaciones aceptadas.

## Síntoma

Desde P4T-PVE1 (`192.168.50.18/27`) los intentos ICMP a QDevice (`192.168.90.28`) obtuvieron pérdida total. El trazado identificó un rechazo administrativo en CorevIOS-1 (`192.168.50.2`): `!A`.

## Impacto

No queda acreditada la prueba ICMP exigida originalmente para QDevice desde la VM anidada. No se puede aprobar P4.3 ni crear el clúster con esta evidencia. El flujo funcional posterior de QNetd es TCP/5403, por lo que debe verificarse explícitamente antes de concluir si la conectividad de servicio está afectada.

## Evidencia

Ver [captura P4T-PVE1](2026-08-31_P4.3_PVE-1_captura.txt). Salidas aportadas:

```text
ping -c 4 192.168.90.28
4 packets transmitted, 0 packets received, 100% packet loss

traceroute 192.168.90.28
1  192.168.50.2 (192.168.50.2) ... !A
```

## Acción y rollback aplicado

No se aplicó ningún cambio. Se conserva P4T-PVE1 para diagnóstico; no se creó el clúster, no se modificaron ACL, red, QDevice ni VMs definitivas.

## Resultado de prueba funcional

```text
$ nc -z -w 3 192.168.90.28 5403
$ echo $?
1
```

El flujo TCP/5403 tampoco quedó disponible desde P4T-PVE1. La salida `1` no distingue por sí sola rechazo ACL, timeout o puerto inaccesible; el rechazo administrativo ICMP previo identifica que existe filtrado en el tránsito hacia VLAN 90, pero se requiere captura del equipo de red para atribuir la causa del TCP.

## Causa identificada

La captura real de CorevIOS-1 muestra que `VLAN_50_IN` está adjunta **in** a Vlan50 y sólo permite hacia VLAN 90 ICMP `echo-reply` y TCP `established`; no autoriza el SYN TCP nuevo de PVE-1 `.10` ni PVE-2 `.11` a QDevice `.90.28:5403`. La línea `80 deny ip 192.168.50.0 0.0.0.31 192.168.0.0 0.0.255.255` registró 18 coincidencias. `VLAN_90_IN` permite el retorno (`permit ip any 192.168.90.0 0.0.0.31`). Ver [pre CorevIOS-1](2026-08-31_P4.3_CorevIOS-1_pre.txt).

CorevIOS-2, HSRP Standby para ambas VLAN, muestra los mismos adjuntos y líneas de ACL. Ver [pre CorevIOS-2](2026-08-31_P4.3_CorevIOS-2_pre.txt).

## Decisión de corrección y excepción de prueba

El operador autorizó una corrección mínima en ambos Core, antes de la denegación interna de `VLAN_50_IN`:

```cisco
75 permit tcp host 192.168.50.10 host 192.168.90.28 eq 5403
76 permit tcp host 192.168.50.11 host 192.168.90.28 eq 5403
```

Para cumplir la compuerta de red anidada con evidencia desde las VMs temporales, autorizó además estos permisos ICMP de duración estrictamente limitada a P4.3:

```cisco
77 permit icmp host 192.168.50.18 host 192.168.90.28 echo
78 permit icmp host 192.168.50.19 host 192.168.90.28 echo
```

Las líneas 77/78 se retiran en ambos Core después de probar y antes de persistir. No se trasladan a las ACL normativas PFT de P3.

## Mitigación parcial comprobada

Tras la excepción ICMP temporal autorizada, P4T-PVE1 recibió respuesta ICMP de QDevice `.90.28` 4/4, sin pérdida. El incidente permanece abierto hasta comprobar QNetd TCP/5403 desde PVE-1/PVE-2, capturar el post de ambos Core y retirar las líneas temporales 77/78.

La reprueba desde PVE-1 de QNetd TCP/5403 devolvió código `0`; CorevIOS-1 registró `1 match` en la secuencia 75. Ambos Core contienen las secuencias 75–78. La causa que impedía el flujo PVE-1→QDevice queda corregida, pero el incidente se conserva abierto hasta completar PVE-2 y retirar la excepción ICMP temporal. Ver [post Core](2026-08-31_P4.3_CorevIOS_post.txt).

La prueba a Web confirmó que `vmbr0` y el encaminamiento hacia DMZ funcionan:

```text
$ ping -c 4 192.168.100.6
4 packets transmitted, 4 packets received, 0% packet loss
round-trip min/avg/max = 3.244/5.509/11.725 ms
```

## Condición de reanudación

1. Capturar los adjuntos, líneas y contadores reales de `VLAN_50_IN`/`VLAN_90_IN` en CorevIOS-2 antes de modificarlo.
2. Conservar pre/post y aplicar en ambos Core, uno por vez, únicamente los permisos TCP/5403 de `.10/.11` a `.90.28` antes de la denegación interna; verificar desde PVE-1/PVE-2 y comprobar contadores. No abrir permisos para las IP temporales `.18/.19` de forma permanente.
3. Completar la VM temporal en PVE-2, las pruebas bidireccionales, las tablas MAC y el retiro de ambas VMs antes de cualquier aprobación de P4.3.

## Cierre funcional — 2026-09-14

En el cierre de P4.4, PVE-1 y PVE-2 alcanzaron `192.168.90.28:5403` por TCP; desde ambos, TCP/22 a QDevice volvió a estar bloqueado después de retirar la excepción temporal. `pvecm status` mostró `Quorate: Yes` y la bandera `Qdevice`. Las secuencias temporales 77/78 no existen en los Core. Esto resuelve el flujo de servicio QNetd y la excepción temporal; no convierte en ejecutadas las pruebas de P4T-PVE2, VM-a-VM o MAC, aceptadas manualmente como limitaciones en el control P4.3.
