# S3.1 — Preestado de access ports PVE-2

Fecha: 2026-09-22 (UYT, UTC-03:00)
Tarea: S3.1
Tipo: pre
Estado: Aprobado al cierre de la verificación; este archivo conserva el síntoma inicial.

## Topología runtime

API GNS3 local, proyecto `PFT-sprint2-preview1`, estado `opened`, versión `2.2.61`:

```text
PVE-2 adapter 1/0  <->  AccvIOS-1 adapter 7/0
PVE-2 adapter 0/0  <->  AccvIOS-1 adapter 8/0
```

La numeración del API no coincide literalmente con el nombre de interfaz que
presenta IOSv en consola. La correlación observada en el equipo es:

```text
adapter 7/0 -> Gi1/3 -> gestión PVE-2, VLAN 110
adapter 8/0 -> Gi2/0 -> bridge de VMs PVE-2, VLAN 115
```

## Estado observado antes de generar tráfico desde PVE-2

En `AccvIOS-1` ambos enlaces estaban `connected` y en modo access. `Gi1/3`
estaba en VLAN 110 y `Gi2/0` en VLAN 115. La tabla dinámica ya aprendía la
MAC `BC:24:11:13:35:71` de DC2 en `Gi2/0`, pero en la primera muestra no
aparecía la MAC de gestión `0C:6A:8F:9B:00:01` en `Gi1/3`.

En la consola de PVE-2 se verificó:

```text
vmbr1: 192.168.110.10/27
default via 192.168.110.1 dev vmbr1
ss: 0.0.0.0:22 y *:8006 en LISTEN
ping -c 3 192.168.110.1: 3 recibidos, 0% pérdida
```

La discrepancia era de aprendizaje de MAC/bridge, no una evidencia de que el
puerto estuviera en una VLAN equivocada. No se aplicó `shutdown/no shutdown` ni
se cambió la configuración de los access ports durante este diagnóstico.
