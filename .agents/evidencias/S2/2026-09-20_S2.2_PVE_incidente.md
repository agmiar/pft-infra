# S2.2 — Incidente de acceso SSH durante la retirada

- Fecha: 2026-09-20 (UYT, UTC-03:00).
- Tarea: S2.2.
- Estado del incidente: Resuelto.
- Estado final de S2.2: Aprobado.

## Síntoma

En PVE-1, después de detener `pve-cluster` como parte de la retirada, un nuevo intento SSH desde PVE-2 devolvió `Permission denied (publickey,password)`. El acceso de gestión por `vmbr1` seguía configurado, pero no se continuó con comandos remotos hasta recuperar una consola fiable.

## Impacto

La retirada de PVE-1 quedó interrumpida temporalmente antes de mover sus archivos activos. No se borraron VMs, discos, redes ni configuraciones de VM. PVE-2 ya estaba independiente y no fue afectado.

## Evidencia

- La salida del intento SSH registró `Permission denied (publickey,password)`.
- La consola VNC local de PVE-1 mostró un prompt root y permitió ejecutar una acción de recuperación controlada.
- Después, `systemctl is-active pve-cluster` en PVE-1 devolvió `active` y SSH volvió a funcionar.
- El postestado final está en `2026-09-20_S2.2_PVE_post.txt`.

## Recuperación aplicada

Por la consola VNC de PVE-1 se ejecutó únicamente `systemctl start pve-cluster`. Con la sesión SSH ya establecida, se completó la secuencia única: detener `pve-cluster`, iniciar `pmxcfs -l`, mover los archivos Corosync/QDevice a `/root/s2.2-pre-20260920/`, detener el proceso local y reiniciar `pve-cluster`. Finalmente se detuvo `corosync`, que había quedado iniciado durante el arranque del servicio.

## Condición de reanudación

La tarea se reanudó sólo cuando PVE-1 aceptó SSH, `pve-cluster` quedó activo y los backups existían. La aceptación se realizó con el postestado de ambos PVE y la consulta API de GNS3.

## Limitación

No se determinó con certeza si el rechazo inicial se debió a la ubicación de las claves autorizadas en el filesystem de Proxmox; se registra sólo el síntoma observable y la recuperación aplicada.
