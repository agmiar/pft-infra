# S2.2 — Retiro del clúster PVE/QDevice del diseño activo

- Fecha de inicio: 2026-09-20 (UYT, UTC-03:00).
- Estado: Aprobado.
- Objetivo: dejar PVE-1 y PVE-2 como nodos Proxmox independientes, retirar el clúster Corosync/QDevice del diseño activo y conservar la recuperación manual como operación aceptada.
- Límite: no borrar VMs, discos, almacenamiento, antecedentes ni la VM GNS3 `PVE-QDEVICE`.

## Precondiciones

- [x] El operador confirmó iniciar S2.2.
- [x] S2.1 está aprobada: gestión separada en `vmbr1` y bridges de VMs en la NIC de datos.
- [x] Preestado runtime de PVE-1 y PVE-2 capturado antes del cambio.
- [x] El clúster legado está sin quorum; no se usarán cambios de red para recuperarlo.
- [x] Rollback preparado con copias locales de configuración Corosync/QDevice y configuración de VMs.

## Comandos/acciones ejecutados

Se registrarán únicamente comandos y acciones realmente ejecutados, sin credenciales, claves ni secretos.

- Preestado capturado en `2026-09-20_S2.2_PVE_pre.txt`.
- Se respaldaron en cada PVE los archivos de clúster/QDevice y la configuración de VMs antes de retirarlos.
- Se detuvieron y deshabilitaron `corosync` y `corosync-qdevice`.
- Se retiraron los archivos activos de configuración de Corosync mediante modo local de `pmxcfs`; se conservaron copias para rollback.
- Se mantuvo `pve-cluster` activo como filesystem local de Proxmox.
- Se verificaron gestión, inventario de VMs, ausencia de configuración de clúster/QDevice y condición de recuperación manual.

## Resultado

**Aprobado.** PVE-1 y PVE-2 quedaron independientes: `pve-cluster` activo como filesystem local, `corosync` y `corosync-qdevice` inactivos/deshabilitados, sin `/etc/pve/corosync.conf` ni configuración local de Corosync. Las VMs DC1/DC2 y sus configuraciones permanecen conservadas y detenidas. La recuperación queda declarada manual; no existe reinicio automático de VMs, replicación `pvesr` ni recurso HA acreditado. La prueba y sus limitaciones están en `2026-09-20_S2.2_PVE_prueba.md`.

## Rollback

Si la retirada falla, detener el procedimiento; restaurar sólo las copias de configuración capturadas en cada PVE, reactivar los servicios estrictamente necesarios y verificar que no se hayan alterado VMs, discos ni redes. La eventual reconstitución del clúster requerirá una decisión posterior y no forma parte de este rollback automático.

## Siguiente paso

No avanzar automáticamente. S2.3 puede inventariar/ajustar las VMs sobre estos nodos independientes; S2.4 deberá documentar la operación y recuperación manual.
