# S2.1 — Separación de gestión PVE y bridges de VMs

- Fecha de inicio: 2026-09-20 (UYT, UTC-03:00).
- Estado: Aprobado.
- Objetivo: separar la gestión de PVE de la red de VMs mediante la segunda NIC y conservar el bridge de VMs sobre la NIC de datos.
- Resultado exigido: PVE-1 con gestión `192.168.90.20/27`, PVE-2 con gestión `192.168.110.10/27`, acceso administrativo sólo desde las redes de gestión y persistencia comprobada.

## Precondiciones

- [x] El operador confirmó iniciar S2.1.
- [x] El proyecto GNS3 `PFT-sprint2-preview1` está abierto y la API local responde.
- [x] GNS3 informa PVE-1 y PVE-2 iniciados.
- [x] La topología API muestra dos NIC por PVE: `eth0` hacia ADvIOS-9a/9b y `eth1` hacia `SwitchvIOSL3-1`.
- [x] Preestado runtime de ambos PVE capturado desde consola.
- [x] Puertos de gestión de los switches confirmados y configurados en las VLAN objetivo.
- [x] Rollback preparado con copias de `/etc/network/interfaces`, estado de bridges y enlaces GNS3.

## Comandos/acciones ejecutados

Se registrarán aquí únicamente comandos y acciones realmente ejecutados, sin credenciales ni secretos.

- Se capturó el preestado API/runtime en `2026-09-20_S2.1_PVE_pre.txt`.
- Se configuró ADvIOS-1 Gi1/0 como acceso VLAN 90 para PVE-1 y AccvIOS-1 Gi1/3 como acceso VLAN 110 para PVE-2; se guardó la configuración en ambos switches.
- Se reemplazaron los enlaces de las segundas NIC en GNS3: PVE-1 eth1 a ADvIOS-1 Gi1/0 y PVE-2 eth1 a AccvIOS-1 Gi1/3.
- Se respaldó `/etc/network/interfaces` en cada PVE como `/etc/network/interfaces.s2.1.pre`.
- En PVE-1 se dejó `vmbr0` sin IP sobre `ens3` para VMs y se creó `vmbr1` sobre `ens4` con `192.168.90.20/27` y gateway `192.168.90.1`.
- En PVE-2 se dejó `vmbr0` sin IP sobre `ens3` para VMs y se creó `vmbr1` sobre `ens4` con `192.168.110.10/27` y gateway `192.168.110.1`.
- Se ejecutó `ifreload -a` en ambos PVE.
- Desde Alpine se verificaron ping, TCP/22 y TCP/8006 hacia ambos PVE.
- Desde GuestPC-1 se verificó que ambos destinos de gestión resultan inalcanzables.
- Se ejecutó `ifquery --check -a` en ambos PVE con código de salida 0.

## Resultado

S2.1 queda aprobado por la separación comprobada de bridges, las IP de gestión persistentes, la conectividad administrativa desde Alpine y la falta de conectividad desde GuestPC-1. `pvecm status` posterior muestra el clúster legado sin quorum al retirar las IP antiguas; la retirada del clúster/QDevice corresponde a S2.2 y no se declara resuelta aquí. Las VMs de prueba permanecían detenidas, por lo que no se acredita tráfico de una VM en producción sobre `vmbr0`.

## Rollback

Si una modificación falla, retirar sólo los cambios de S2.1: restaurar el archivo de red respaldado, devolver las IP/gateway/bridge al preestado y reponer exclusivamente los enlaces GNS3 alterados. Verificar después SSH/8006 y la conectividad de las VMs por el bridge de datos.

## Siguiente paso

No avanzar automáticamente. S2.2 debe retirar el clúster/QDevice legado y S2.3 debe continuar con las VMs, usando las evidencias de S2.1 como precondición.
