# Incidente P5.4 — WIN-MGMT-01 no completa el primer arranque

- **Fecha:** 2026-09-23
- **Tarea:** P5.4 — estaciones Windows de gestión
- **Estado:** Fallido

## Síntoma

Tras una fase `Getting ready` prolongada con actividad sostenida de CPU y
escritura en disco, se conservó la ISO montada, se cambió la prioridad de
arranque a disco y se realizó un reinicio controlado de `WIN-MGMT-01`. La consola
VNC mostró una pantalla azul con el stop code `CRITICAL_PROCESS_DIED`, al 97 % de
la recopilación de información.

Tras el reinicio automático, la pantalla de recuperación indicó que el sistema
operativo no podía iniciar correctamente, con código `0xc0000001`.

## Impacto

`WIN-MGMT-01` no queda disponible para DHCP, DNS, unión a `pft.test`, aplicación
de GPO ni pruebas de acceso a PVE. P5.4 no puede aprobarse y P3.4 aún no puede
usar este cliente de VLAN 90.

## Evidencia

- `2026-09-23_P5.4_Windows-MGMT_control.md`.
- Consola VNC local de `WIN-MGMT-01`, observada el 2026-09-23.
- `2026-09-23_P5.4_Windows-MGMT_pre.txt` y
  `2026-09-23_P5.4_Windows-MGMT_post.txt`.

## Rollback aplicado

Ninguno destructivo. Se preservan el disco QCOW2 de 50 GiB, el overlay original
renombrado y los enlaces VLAN 90. No se modificaron ACL ni configuración de red.

## Condición de reanudación

Diagnosticar el fallo de primer arranque y recuperar o reinstalar la estación
sobre un disco nuevo preservando el estado actual como evidencia. Antes de
reemplazar cualquier disco se debe capturar el preestado correspondiente.

## Reanudación aplicada

Se detuvo únicamente `WIN-MGMT-01`, se preservó su disco fallido con sufijo
`.incidente-20260923` y se creó un QCOW2 nuevo, independiente, de 50 GiB en el
mismo directorio del proyecto en Redalco. La VM se inició desde la ISO y el
instalador verificó `Drive 0 Unallocated Space` de 50.0 GB; la copia de archivos
comenzó. `WIN-MGMT-02` no fue reiniciada ni modificada durante esta recuperación.

Durante el reinicio automático posterior del instalador, la consola VNC dejó de
aceptar conexión y el host Ubuntu/GNS3 dejó de responder por SSH. No se aplicó
ningún cambio adicional mientras el host no está disponible.

El host volvió a responder y reportó un uptime inferior a un minuto. La
verificación posterior mostró que GNS3, los proxies noVNC y los procesos QEMU de
ambas estaciones no se recuperaron automáticamente; por tanto no había consola
ni VM activa al momento de la comprobación.

Se recuperaron manualmente el servicio GNS3 local, el proyecto y las cuatro
instancias necesarias para la recuperación (`ADvIOS-1`, `ADvIOS-2`,
`WIN-MGMT-01` y `WIN-MGMT-02`). La ISO y el disco base permanecen en Redalco;
para que el servidor GNS3 acepte sus rutas se usaron enlaces simbólicos locales,
sin duplicar esos archivos. La nueva instalación de `WIN-MGMT-01` quedó iniciada
desde la ISO, pendiente de comprobación visual de su progreso.

Más tarde, desde la estación de administración, el host `192.168.1.190` dejó de
responder tanto a ICMP como a SSH. La estación sigue en la subred
`192.168.1.0/24`, pero el host no aparece en su caché ARP. No se hicieron cambios
adicionales mientras no exista acceso administrativo al host.

## Corrección de visibilidad del plano GNS3

La verificación por API del proyecto activo confirmó que `WIN-MGMT-01` y
`WIN-MGMT-02` están iniciados y enlazados respectivamente a `ADvIOS-1 Gi0/5` y
`ADvIOS-2 Gi0/5`. Dos nodos QEMU heredados, antes llamados `mgmtPC-1` y
`mgmtPC-2`, no tenían enlaces y podían confundirse con los clientes nuevos. Se
preservaron, se renombraron `LEGACY-mgmtPC-1-preserved` y
`LEGACY-mgmtPC-2-preserved`, y se movieron fuera del área principal. Las estaciones
Windows se situaron debajo de sus ADvIOS correspondientes. No se modificaron ACL,
SVI ni parámetros de red.
