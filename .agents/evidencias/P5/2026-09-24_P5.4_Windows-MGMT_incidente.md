# Incidente P5.4 — canal de comprobación de estaciones bloqueado

- **Fecha:** 2026-09-24
- **Tarea:** P5.4
- **Estado:** Bloqueado

## Síntoma histórico

La primera comprobación automatizada de `WIN-MGMT-02`, con la cuenta de dominio `Administrator@pft.test` seleccionada, mostró `The password is incorrect` porque la credencial fue tecleada incorrectamente. El operador confirmó que la contraseña funciona y dejó la estación autenticada. En la misma inspección, `WIN-MGMT-01` figuraba detenido en la API GNS3; se inició una vez y quedó `started`, mostrando la pantalla de bloqueo tras el arranque.

## Impacto

No es posible ejecutar de forma reproducible desde ambas estaciones la verificación de OU/GPO ni las pruebas TCP/22 y HTTPS/8006 contra `192.168.50.10` y `192.168.50.11`. P5.4 no puede aprobarse.

## Rollback aplicado

No se aplicó rollback técnico: no se cambiaron ACL, red, cableado, DHCP, DNS ni GPO. El arranque de `WIN-MGMT-01` fue el único cambio operativo y es reversible apagando la VM con autorización; se conservaron sus discos y enlaces.

## Revalidación posterior

- `WIN-MGMT-02` quedó en el escritorio como `PFT\\Administrator`; `System Information` identificó `WIN-MGMT-02`.
- `rsop.msc` abrió un informe real de equipo/usuario y cargó `Windows Settings > Security Settings` en ambos árboles.
- Las dos URLs HTTPS PVE y el intento gráfico contra TCP/22 desde `WIN-MGMT-02` no dieron una respuesta positiva; se conserva el detalle en [estaciones](2026-09-24_P5.4_Windows-MGMT_estaciones-mgmt.md) y [postestado](2026-09-24_P5.4_Windows-MGMT_post.txt).
- `WIN-MGMT-01` quedó en la pantalla de inicio después de un único intento con `PFT\\Administrator`, que mostró el aviso genérico de usuario/contraseña incorrectos. No se hicieron reintentos ni variantes.

## Condición de reanudación

Autenticar `WIN-MGMT-01`, identificar la OU exacta y las GPO efectivas en ambas estaciones, y resolver o documentar el motivo por el que PVE-1/PVE-2 no entregan login/certificado desde VLAN 90. Repetir las cuatro pruebas PVE desde cada estación, capturando resultados sin credenciales.

## Revalidación posterior — 2026-09-24

- `WIN-MGMT-01` quedó autenticado y permitió generar RSoP. Se observaron `PFT\\Administrator`, `PFT\\WIN-MGMT-01`, políticas de usuario/equipo procesadas y `Windows Settings > Security Settings`.
- La estación recibió por DHCP `192.168.90.11/27`, gateway `192.168.90.1`, DHCP `192.168.90.2` y DNS `192.168.50.12/.13`, con sufijo `pft.test`.
- HTTPS/8006 hacia PVE-1 y PVE-2 y la comprobación gráfica HTTP/22 contra ambos destinos devolvieron `Can't reach this page`; no hay evidencia positiva de los cuatro accesos.
- Al reconectar `WIN-MGMT-02`, la consola quedó en la pantalla de inicio `Administrator@pft.test`; la comprobación quedó pendiente y no se introdujeron credenciales.

El incidente sigue **Bloqueado**. No se aplicó rollback técnico ni cambios de red; la condición de reanudación es dejar WIN-MGMT-02 en un escritorio de dominio y obtener una prueba positiva o un diagnóstico autorizado del camino VLAN 90 hacia PVE.

## Revalidación final — 2026-09-24

- El operador dejó `WIN-MGMT-02` en el escritorio. `System Information` identificó `WIN-MGMT-02`; RSoP mostró `PFT\\Administrator` y `PFT\\WIN-MGMT-02`, y cargó la configuración de equipo/usuario y `Windows Settings > Security Settings`.
- DHCP real de WIN-MGMT-02: `192.168.90.12/27`, gateway `192.168.90.1`, DHCP `192.168.90.2`, DNS `192.168.50.12/.13`, sufijo `pft.test`.
- HTTPS/8006 contra PVE-1/PVE-2 y las comprobaciones gráficas HTTP/22 contra ambos destinos devolvieron `Can't reach this page`. No se obtuvo login, aviso de certificado ni prueba concluyente de socket TCP/22.
- No se aplicó rollback ni se modificó ACL, red, DHCP, DNS, GPO o cableado.

El incidente permanece **Bloqueado**. La condición de reanudación es demostrar la OU/GPO nominales y obtener una prueba de socket TCP/22 y/o una respuesta positiva HTTPS/8006 desde cada estación, o documentar con evidencia autorizada el bloqueo en VLAN 90.

## Diagnóstico adicional — 2026-09-24

Internet Explorer informó `INET_E_CANNOT_CONNECT` para HTTPS/8006 hacia PVE-1 y PVE-2 y para las dos comprobaciones gráficas del puerto 22 desde WIN-MGMT-02. El resultado acota el síntoma a falta de conexión de navegador, pero no permite distinguir ACL, ruta, servicio o firewall. No se cambiaron ACL ni red.


## Diagnóstico del camino ACL pendiente — 2026-09-24

- Se intentó abrir SSH al host Ubuntu/GNS3 `192.168.1.190` para consultar, en modo lectura, los contadores de `PFT_V90_FUNC_IN` y el estado de PVE.
- El host respondió al transporte SSH, pero rechazó la única credencial operativa disponible. No se probaron variantes ni se ejecutaron comandos en el host.
- Impacto: no fue posible correlacionar todavía el `INET_E_CANNOT_CONNECT` con ACL, ruta, servicio PVE o firewall.
- Rollback: ninguno; la sesión se cerró y no se modificó ningún equipo.
- Condición de reanudación: restablecer el acceso SSH operativo al host o proporcionar una consola de sólo lectura autorizada para consultar los Cores/PVE.

## Corrección de diagnóstico y arranque — 2026-09-24

- La cuenta SSH correcta del operador permitió acceder al host Ubuntu/GNS3; el rechazo anterior correspondía al usuario SSH equivocado, no a una credencial que deba probarse de nuevo.
- El preestado API confirmó que ambas VMs Windows estaban `stopped`. Se inició sólo cada VM, con HTTP `200`, y la API confirmó `started` para ambas.
- Las consolas VNC ahora muestran la pantalla de bloqueo de Windows. No se automatiza Lock Screen ni se introducen credenciales sin que el operador desbloquee las estaciones.
- No hubo rollback ni cambios de ACL, red, DHCP, DNS, GPO o cableado.

## Incidente de port-security en WIN-MGMT-01 — 2026-09-24

- **Síntoma:** después del movimiento de `Administrator`, `gpupdate /force` en `WIN-MGMT-01` falló para equipo y usuario indicando falta de conectividad con un controlador de dominio; `WIN-MGMT-02` aplicó correctamente `PFT-Baseline-Users`.
- **Evidencia de sólo lectura:** en `ADvIOS-1 Gi1/1` el enlace está `up/up`, pero port-security está habilitado en modo `Restrict`, con dos direcciones sticky y `Security Violation Count: 97`. La última fuente observada es `0c80.6b32.1001` en VLAN 90, mientras la tabla sticky contiene `0c45.ee75.0000` y `0c80.6b32.0000`.
- **Comparación:** `ADvIOS-2 Gi1/1` está `Secure-up`, con `Security Violation Count: 0`, última fuente `0c80.6b32.1002` en VLAN 90 y sticky consistente con MGMT-02.
- **Impacto:** los frames de la estación MGMT-01 pueden ser descartados en su puerto de acceso; no se puede validar GPO de usuario ni autenticación de dominio en esa estación hasta corregir o documentar el port-security.
- **Rollback aplicado:** ninguno; sólo se ejecutaron consultas `show` y no se modificaron ACL, VLAN, port-security, cableado ni GPO.
- **Condición de reanudación:** capturar preestado adicional y recibir autorización explícita para corregir la asociación sticky de `ADvIOS-1 Gi1/1`; después repetir `gpupdate /force` y `gpresult /r /scope user` en MGMT-01.

## Corrección autorizada de port-security en WIN-MGMT-01 — 2026-09-24

- Se capturó el preestado de `ADvIOS-1 Gi1/1`: `Restrict`, máximo 2, sticky `0c45.ee75.0000`/`0c80.6b32.0000`, 97 violaciones y última fuente `0c80.6b32.1001` en VLAN 90.
- Con autorización del operador se retiraron las sticky antiguas, se registró `0c80.6b32.1001` como sticky y se reactivó port-security en el mismo puerto, conservando VLAN 90, máximo 2, `Restrict`, portfast y el resto de la interfaz.
- Postestado: `Secure-up`, una sticky `0c80.6b32.1001`, `Security Violation Count: 0` y tabla MAC estática de VLAN 90 consistente. La configuración quedó guardada en startup-config.
- No se modificaron ACL, SVI, VLAN, DHCP, DNS, GPO ni cableado. Rollback: restaurar las dos líneas sticky anteriores y retirar la nueva MAC, sólo si el operador lo solicita.

## Incidente real de OU/GPO — 2026-09-24

- **Síntoma:** `gpresult /r /scope computer` mostró en ambas estaciones el objeto bajo `CN=Computers,DC=pft,DC=test`, no bajo la OU de gestión prevista.
- **GPO aplicada:** en ambos casos sólo aparece `Default Domain Policy`; no aparecen las GPO PFT previstas.
- **Impacto:** la aceptación de OU/GPO de P5.4 falla; no puede declararse que las estaciones reciban la política de gestión.
- **Evidencia:** [estado de estaciones](2026-09-24_P5.4_Windows-MGMT_estaciones-mgmt.md) y [postestado](2026-09-24_P5.4_Windows-MGMT_post.txt).
- **Rollback:** ninguno; no se movieron objetos ni se modificaron GPO, vínculos o filtros.
- **Condición de reanudación:** autorización explícita para mover ambos objetos a la OU prevista y/o corregir los vínculos o filtros; después ejecutar `gpupdate` y repetir `gpresult` en ambas estaciones.

## Corrección autorizada y estado posterior — 2026-09-24

- La autorización fue recibida. El preestado confirmó ambos objetos en `CN=Computers,DC=pft,DC=test` y la OU destino con las cinco GPO PFT heredadas.
- Se movieron únicamente `WIN-MGMT-01` y `WIN-MGMT-02` a `OU=Computers,OU=MGMT-VLAN90,OU=Zones,OU=PFT,DC=pft,DC=test`.
- El postestado confirmó los dos DN en la OU prevista y los seis vínculos efectivos incluyendo `Default Domain Policy`.
- `Invoke-GPUpdate` desde DC1 no alcanzó las estaciones por administración remota de tareas deshabilitada o equipos no respondientes; no se cambió ese control.
- Rollback disponible: devolver cada objeto a su DN anterior bajo `CN=Computers,DC=pft,DC=test`, sólo si el operador lo solicita.
- Condición actual: ejecutar `gpupdate /force` localmente en ambas estaciones y repetir `gpresult /r /scope computer` y `/scope user`.

## Revalidación después del arranque y diagnóstico de infraestructura — 2026-09-24

- El operador desbloqueó ambas estaciones. Se repitieron desde MGMT-01 y MGMT-02 las URLs HTTPS/8006 de PVE-1/PVE-2 y los sondeos gráficos HTTP/22; las ocho comprobaciones mostraron `Can't reach this page`. MGMT-02 mostró `INET_E_CANNOT_CONNECT` en sus cuatro URLs al expandir la información.
- La consulta de sólo lectura al host Ubuntu/GNS3 confirmó PVE-1/PVE-2 `started`, escucha en TCP/22 y TCP/8006, `pve-firewall` deshabilitado y puertos de switch `connected` en access VLAN 50. El canal temporal `172.31.255.2/.3` respondió TCP/22, TCP/8006 y HTTPS 200.
- En CorevIOS-1, `PFT_V90_FUNC_IN` contiene las reglas 22/8006 para `.10/.11`, pero esas cuatro entradas no mostraron coincidencias en el contador capturado. El sondeo local del Core hacia PVE-1 recibió SYN-ACK en `tcpdump`, mientras `PFT_V50_FUNC_IN` registró la denegación del retorno hacia la IP del Core. El registro completo está en [diagnóstico PVE](2026-09-24_P5.4_PVE_diagnostico_control.md).
- Esto demuestra que el síntoma no era sólo que las estaciones estuvieran apagadas. No se declara aún un único origen para el tráfico Windows: siguen abiertas las hipótesis de ACL de retorno/camino productivo y falta la prueba de socket desde Windows.
- No se aplicó rollback ni se modificó ACL, red, servicios, DHCP, DNS, GPO, cableado o discos.

El incidente permanece **Bloqueado**. Condición de reanudación: autorizar una corrección/revisión del camino ACL o retorno con preestado nuevo, y obtener desde cada Windows una prueba de socket TCP/22 y una respuesta positiva HTTPS/8006; además, demostrar OU/GPO nominales.

## Resolución del incidente y cierre P5.4 — 2026-09-24

- La causa operativa de la falta de conectividad de `WIN-MGMT-01` quedó corregida: `ADvIOS-1 Gi1/1` tenía la VLAN 90 en `startup-config`, pero el estado en ejecución había quedado en VLAN 1 después del arranque. Bajo autorización se reaplicó `switchport access vlan 90` y se persistió con `write memory`.
- Postestado: access VLAN 90, port-security `Secure-up`, MAC `0c80.6b32.1001` en VLAN 90 y cero violaciones.
- DHCP/ARP confirmó `.90.11` para MGMT-01 y `.90.12` para MGMT-02. `gpupdate /force` finalizó correctamente en MGMT-01.
- La salida visible de `gpresult /r /scope user` en ambas estaciones mostró `PFT-Baseline-Users` aplicada para `PFT\\Administrator`; las OU de usuario y estaciones, las GPO de equipo y el acceso PVE están documentados en las evidencias enlazadas.
- Rollback disponible: retirar el acceso VLAN 90 de `ADvIOS-1 Gi1/1` y restaurar la configuración anterior sólo bajo nueva autorización. No se tocaron ACL.

**Estado final del incidente:** Aprobado como resuelto dentro de P5.4. **Estado P5.4: Aprobado.**
