# P5.2 — Bloqueo de acceso administrativo a DC1

**Fecha:** 2026-09-15  
**Tarea:** P5.2  
**Estado:** Bloqueado

## Síntoma

Desde la consola root verificada de PVE-1 se comprobó alcance a DC1 `192.168.50.12`: ICMP respondió y TCP/389, TCP/445 y TCP/5985 estaban abiertos; TCP/3389 expiró. Una petición GET a `/wsman` devolvió HTTP 405 `Allow: POST`, lo que no determina el resultado de autenticación.

Una única solicitud HTTP POST vacía a `http://192.168.50.12:5985/wsman`, usando la referencia Administrator proporcionada por el operador, devolvió HTTP 401 Unauthorized con desafíos `Negotiate` y `Kerberos`. No se envió cuerpo SOAP ni instrucción WMI; no se solicitó ejecutar procesos ni crear archivos. Se detuvo el acceso administrativo sin probar variantes ni repetir la autenticación.

## Impacto

No se pudo consultar dentro de Windows el estado de AD DS/DNS, replicación, zonas y registros configurados, OUs, grupos, membresías, GPO ni vínculos. Tampoco se aplicaron cambios de P5.2. Las consultas DNS anónimas desde PVE sí permitieron obtener SOA y comprobar algunas respuestas A; esos resultados no sustituyen el inventario interno ni demuestran replicación AD.

## Evidencia

- [Preestado parcial PVE y DNS](2026-09-15_P5.2_AD-DNS_pre.txt).
- [Control P5.2](2026-09-15_P5.2_AD-DNS_control.md).
- GET WinRM: HTTP/1.1 405, `Allow: POST`; no se considera autenticación exitosa.
- POST vacío a `/wsman` por WinRM/HTTP: HTTP/1.1 401 Unauthorized; no se envió una solicitud WMI ni se pidió crear procesos o archivos.

No se copiaron contraseñas, ni se guardaron capturas con credenciales. No se confirmó que el proceso temporal solicitado se ejecutara ni que se creara el archivo de sondeo; no se afirma ninguno de esos resultados.

## Impacto sobre cambios y rollback

No hubo cambios en AD/DNS, OUs, grupos, GPO, red, ACL, servicios o configuración de PVE. Durante la comprobación final DC1/VMID 101 se encontró detenida; se ejecutó `qm start 101` para restaurar el estado `running` registrado en el preestado. El [postestado de acceso y quorum](2026-09-15_P5.2_AD-DNS_post.txt) documenta la acción y el quorum final. No se intentó modificar ni rotar ninguna contraseña.

## Condición de reanudación

La referencia proporcionada no autenticó en este canal. No volver a intentar la autenticación hasta recibir una nueva indicación del operador; para reanudar, se necesita un medio de acceso administrativo vigente o un canal alternativo autorizado a DC1/DC2. Después se debe capturar el preestado interno completo y acordar las membresías, el alcance/configuración de GPO y si se requiere zona inversa para VLAN 100 antes de cambios.

## Nueva instrucción de acceso y estado del canal — 2026-09-15

El operador indicó usar la referencia ya proporcionada a través de la consola local de DC1 y autorizó expresamente esa vía. La indicación no cambia el resultado histórico del único POST vacío a WinRM: no se reintentó WinRM ni se envió SOAP/WMI. Tampoco se introdujo la credencial de Windows por consola.

Desde el shell root de PVE-1 se consultó `qm help vncproxy`, que muestra `Proxy VM VNC traffic to std/stdout`, y se probó un puente local para obtener el marco del invitado. La sesión SSH de control a LaptopUbuntu se resetó antes de recibirlo. Las pruebas posteriores desde Windows dieron ping `True` a `192.168.1.190` y TCP `False` para 22, 3080 y 5904; por tanto, no se pudo inspeccionar ni limpiar el helper temporal. DC1 quedó `running` y el quorum siguió 3/3 con QDevice, según el [postestado](2026-09-15_P5.2_AD-DNS_post.txt). P5.2 continúa Bloqueado hasta restablecer el canal local; la condición no depende de recibir otra contraseña o autorización.

## Revalidación tras aviso de alcance — 2026-09-15

El operador indicó que el destino ya estaba alcanzable. Desde el shell Windows del proyecto, `Test-Connection -ComputerName 192.168.1.190 -Count 1 -Quiet` respondió `True`. Las comprobaciones TCP desde esta sesión devolvieron `False` para LaptopUbuntu `192.168.1.190:22`, API GNS3 `192.168.1.190:3080`, relay VNC `192.168.1.190:5904`, y PVE-1 `192.168.50.10:8006` y `:22`. Esto sólo describe la conectividad observada desde este Windows: ICMP llega a LaptopUbuntu, pero ninguno de esos canales TCP está disponible desde aquí. No se intentó autenticación ni se cambió configuración. La hora individual de estas llamadas no se capturó.

## Reanudación parcial del canal — 2026-09-15

La comprobación TCP anterior se hizo desde el entorno sin permiso de red: el SSH directo devolvió `Permission denied` antes de recibir el saludo del host. Tras la indicación del operador, se abrió una sesión SSH directa a LaptopUbuntu `192.168.1.190:22` con autenticación por contraseña forzada; la autenticación a Ubuntu fue correcta. La API GNS3 local confirmó el proyecto activo y sus nodos PVE iniciados, pero la consola PVE-1 quedó en `pve-1 login:` después de un único intento con la referencia PVE proporcionada. No se confirmó un shell administrativo, no se repitió la autenticación y no se introdujo la credencial de Windows. Ver [registro posterior de LaptopUbuntu/GNS3](2026-09-15_P5.2_LaptopUbuntu_post.txt) y [incidente GNS3/acceso](2026-09-15_P5.2_GNS3-access_incidente.md). La última lectura guardada de DC1/quorum sigue siendo anterior a la pérdida de canal; el estado actual no se verificó. P5.2 permanece Bloqueado hasta recuperar un canal administrativo confirmado a PVE y continuar el preestado de Windows.
