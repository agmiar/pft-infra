# P5.2 — Incidente de acceso a la laptop Ubuntu

**Fecha y hora:** 2026-09-15 16:02 UYT  
**Tarea:** P5.2  
**Estado:** Bloqueado

## Síntoma

Desde la sesión local de Windows se ejecutaron estas comprobaciones de solo lectura contra la IP observada de la laptop Ubuntu:

- Test-NetConnection -ComputerName 192.168.1.190 -Port 22 -InformationLevel Quiet → False.
- Test-NetConnection -ComputerName 192.168.1.190 -Port 3080 -InformationLevel Quiet → False.

No se estableció conexión TCP a SSH ni al puerto API de GNS3. No se abrió una sesión SSH, no se autenticó ningún usuario y no se probaron credenciales.

## Comprobación posterior de alcance IP

En la misma sesión Windows se confirmó después que la laptop respondía a nivel IP, aunque los puertos TCP seguían inaccesibles:

- `ipconfig` mostró al host de esta sesión como `192.168.1.186/24`, con gateway `192.168.1.1`.
- `Test-Connection -ComputerName 192.168.1.190 -Count 1 -Quiet` → `True`.
- `arp -a` mostró `192.168.1.190` como vecino dinámico con MAC `84-5c-f3-23-a3-9d`.
- `Test-NetConnection` a TCP/22 y TCP/3080 → `False` en ambos casos.
- El reloj local marcó `2026-09-15 16:12:07 -03:00` después de estas comprobaciones; la hora exacta de cada comando no se capturó.

Esto confirma alcance IP a la laptop, pero no permite distinguir si TCP/22 y TCP/3080 están sin servicio o filtrados. No se probó ningún otro puerto.

## Impacto

No se pudo obtener el preestado actual de DC1/DC2, DNS, OUs, grupos/GPO ni confirmar desde el frontend su IP actual. P5.2 no puede pasar a cambios técnicos ni a pruebas de aceptación. La laptop responde a ping, pero los canales TCP probados no están disponibles; la causa exacta (servicio no disponible o filtrado) queda sin determinar.

## Evidencia

Resultado literal de las pruebas iniciales TCP: False y False, respectivamente. La fecha/hora local registrada fue 2026-09-15 16:02:41 -03:00. En la comprobación posterior, ping fue True, se resolvió el vecino ARP y TCP/22 y TCP/3080 siguieron en False. No se capturaron datos de credenciales.

## Impacto sobre el cambio y rollback

No hubo cambios en GNS3, AD/DNS, red, VMs, servicios, ACL ni configuración. No aplica rollback; no se revirtió ningún estado.

## Condición de reanudación

Habilitar o permitir SSH en la laptop Ubuntu restringiendo el origen a `192.168.1.186`, comprobar TCP/22 desde esta sesión y, si la API GNS3 escucha localmente, acceder a ella por un túnel SSH en vez de exponer TCP/3080. Después acceder a los controladores por el canal de gestión autorizado y capturar el preestado real antes de cualquier escritura. Si una autenticación posterior falla, detenerse y consultar al operador sin probar variantes.
